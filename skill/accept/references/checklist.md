# Clarity checklist

Do not force every item. Add only the ones whose absence would change the result.

| Heading | Question | What goes wrong if it is missing |
|---|---|---|
| Purpose | What is this for? Who will use it? | Wrong solution, misunderstanding |
| Scope | What exactly will be done, and what will not? | Too little or too much work |
| Context | Which project, which file, what was discussed before? | Code built from scratch that does not fit |
| Environment | Operating system, language/version, shell, libraries? | Commands or code that do not run (usually comes from `context.md`) |
| Input | What will be worked on? File, format, sample data? | Wrong format assumed |
| Output | What will be delivered? File, format, where? | Result in the wrong place or format |
| Limits | Dependencies, performance, security, places not to touch? | Unwanted changes |
| Success criteria | What does "done" mean? How will it be tested? | Unverified work |

## Signs of ambiguity

- Pronouns and vague phrases: "this", "that thing", "fix it", "make it better".
- Adjectives without a measure: "fast", "nice", "simple" (compared to what?).
- Terms with several meanings: "voice changer" (live or on files? which effects?).
- Missing person/purpose: it is unclear who the work is for and why.

## What clarifying must not do

- Narrow the request or silently drop a part of it.
- Use general or veiled wording that hides the real purpose.
- Invent unknown details.
- Turn a simple request into a long specification.
